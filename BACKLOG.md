| 2a | └ Побочный фикс в этой же задаче: лента заявок для юристов (`_refreshCases`) раньше не фильтровала по `status` вообще — заявка с уже принятым юристом всё равно показывалась всем остальным юристам как "активная". Добавлен фильтр `.eq('status','open')` + триггер, переводящий `cases.status` в `closed` при принятии отклика — иначе "снова видна другим юристам" после отказа было бы бессмысленно (она и так всегда была видна) | ✅ часть той же миграции |
| 3 | `moderation_log` — лог отказов обеих сторон для ручного разбора злоупотреблений (частые немотивированные отказы). Доступен только через SQL Editor, автоблокировки нет — есть вью `moderation_decline_stats` для агрегатов по актору | ✅ часть той же миграции |
| 3a | └ При применении обнаружен и закрыт реальный security-баг: вью `moderation_decline_stats` выполняется с правами владельца (Postgres 17, без `security_invoker`) и поэтому обходит RLS на `moderation_log` — а дефолтные grant'ы схемы `public` в этом проекте дают `SELECT` на новые объекты `anon`/`authenticated` автоматически. Итог: любой авторизованный пользователь мог прочитать агрегаты отказов по всем пользователям через API. Закрыто миграцией `20260712_moderation_decline_stats_lockdown.sql` (`REVOKE ALL ... FROM anon, authenticated` на вью и таблицу) | ✅ исправлено |

Обе основные миграции + фикс лока применены через Supabase MCP (`apply_migration`) 12.07.2026. Advisors (security) после применения: только pre-existing находки, не относящиеся к этой сессии — `function_search_path_mutable` и `anon/authenticated_security_definer_function_executable` на давно существующих trigger-функциях (тот же паттерн, что у `consume_free_contact`, `can_review_case` и т.д.), плюс `rls_enabled_no_policy` на `moderation_log` — ожидаемо и по замыслу (доступ только через SQL Editor).
